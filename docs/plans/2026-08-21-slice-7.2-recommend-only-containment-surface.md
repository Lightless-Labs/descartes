## 0. What this plan does NOT do (read this first)

| Concern | Disposition in this plan |
|---|---|

| Mint, verify, or consume a capability token | **NO.** Capability tokens belong to §(e) Slice 7.5+ (execution). Nothing here validates or requires one because nothing here executes. |
| Create `authority/containment.json` or any authority store | **NO.** That is §(e) Slice 7.3 (authority-store scaffold). This surface persists only ordinary alert records via the already-shipped `alert-store.js`. |

| Re-resolve a raw/live target to act on it | **NO.** §(a)'s hash-at-source-vs-raw-identifier tension is respected: this surface never maps a stored hash back to a live target to act, and (v0 default) performs no new live re-resolution at all — see Open Decision 1. |
| Reach the LLM | **NEVER.** The `containment.*` namespace is **hard-excluded** in `classifyAlertNamespace` — `classifyAlertNamespace('containment.recommend.<verb>')` returns `{ namespace: 'containment', hardExcluded: true }`, checked as the SECOND branch (immediately after `learned.`), before any unrecognized-prefix fallback. ## 1. Problem statement + why now

The observed incident that motivates the whole Slice-7 initiative (`docs/plans/
2026-07-13-observed-incident-collectors.md` §Origin) was a mass termination of worker sessions
coincident with unattributed odd-hour logins, during which an AI agent mutated host state with **no
approval gate**. Descartes now *detects* that incident class deterministically — `session.count_drop`/
`session.churn`, `peer.count_spike`, `canary.tripped`, and the process-lineage/child-spawn anomaly
detector (shipped `6238f7e`) all fire without an LLM — but the operational lifecycle stops at
**Notify**. There is no **Recommend** stage for containment: an operator who receives
"mass session drop detected" gets no proposed next action, and Descartes has no surface on which to
say "consider investigating/quarantining X" without either (a) staying mute, or (b) leaping straight
to the far more dangerous **Act** stage that Slice 7 spent three review rounds fencing off.

**Why now.** Slice 7 is **UNBLOCKED** as of 2026-08-11: the operator signed off all nine §(d) scope
decisions, and §(d) item 6 explicitly directs **BUILD**, with a concrete phased sequence whose first
buildable containment rung is exactly this one — §(e) **Slice 7.2, recommend-only via local
notification** (`docs/HANDOFF.md`, "Remaining threads", 2026-08-11: *"recommend-only via local
notification (Slice 7.2) is the first buildable slice (mutates nothing)"*). It is the correct
lowest-risk starting point because it exercises the **proposal half** of §(c)'s deterministic gate
(the code may *propose* a verb+target; only a future gate + off-machine token could ever authorize
execution) with **none** of the execution risk, and it is the natural near-term consumer of the
fleet MVP's later remote-device notification relay (§(e) Slice 7.4, F2a in the fleet plan). Shipping
it now closes the Observe→Notify→**Recommend** gap for containment while the authority/execution
plane (7.3+) is still design-only.

**Why it is nonetheless sensitive enough to warrant this dedicated plan.** Per §(e) Slice 7.2's own
review clause, *a wrongly-targeted recommendation is itself a harm vector — misdirected operator
trust — even with no execution capability behind it.* An operator who trusts "consider killing PID X"
and acts on a fabricated, stale, or misresolved target does real damage with their own hands. So this
surface inherits the initiative's two hardest invariants in full: **never fabricate a security signal
/ degrade-not-fabricate** (a recommendation built on a garbled or absent trigger must degrade to
nothing, never invent a target), and **hash-at-source** (naming a target must not silently
reintroduce raw-identifier handling the monitoring layers were designed to avoid). Those two are the
adversarial spine of this plan.

## 2. Doors-and-corners / PREREQUISITES

Even though this surface mutates nothing, this repo has been bitten by skipped prerequisites (the
native-notification LaunchServices authorization bug, `docs/HANDOFF.md` 2026-07-22). Each dependency
is called out explicitly. A dedicated `doors-and-corners` skill pass is a **hard precondition** for
implementation, per §(e) Slice 7.2's own review requirement — this section is its written form.

**P1 — Local-notification delivery path (SHIPPED, validated, reused verbatim).** The sole delivery
sink is `notification-delivery.js`'s existing fixed-argv path: macOS `osascript` / `/usr/bin/open
-g -n <DescartesNotifier.app> --args …` (native delivery validated end-to-end on a real Homebrew
host, `v0.0.49`, `docs/HANDOFF.md` 2026-07-22), and the Linux `linux-desktop`/`syslog` and generic
`cli` branches already present in `NOTIFICATION_CHANNELS`. **No new platform primitive, no new
`execFile`, no entitlement, no notifier rebuild.** Corner: `open`'s exit code is unusable, so
delivery status stays `best_effort` for this surface exactly as for every other alert family — this
surface must not claim confirmed delivery it cannot observe (degrade-not-fabricate applies to
delivery status too).

**P2 — No new OS permission / no entitlement / no privileged read.** This surface reads only
Descartes-owned alert history and emits Descartes-owned records. It needs **nothing** beyond what
the read-only monitoring layer already has. The one honest corner where a permission *would* be
needed — performing a fresh **live** re-enumeration to name a raw target in cleartext (the
execution-time re-resolution §(a) mandates for real verbs) — is **explicitly NOT built here** and is
raised as Open Decision 1. v0 introduces no new read capability.

**P3 — Trigger signals must already be shipped and their exact rule_ids pinned.** The recommendation
is a deterministic fixed map from an existing anomaly rule_id to a proposed verb. The candidate
triggers (all shipped, all deterministic/non-LLM, all `unknown_namespace` today) are pinned to the
**exact exported constants** `alert-intelligence.js` already imports, not prefix globs:
`SESSION_COUNT_DROP_RULE_ID` / `SESSION_CHURN_RULE_ID` (`session-baseline.js`, Slice 4),
`PEER_COUNT_SPIKE_RULE_ID` (`peer-baseline.js`, Slice 4b), `CANARY_TRIPPED_RULE_ID` /
`CANARY_TAMPERED_RULE_ID` (`canary-baseline.js`, canary v0, `11f94fb`), and
`PROCESS_LINEAGE_NOVEL_EDGE_RULE_ID` (`process-lineage-baseline.js`, `6238f7e`). `[REVIEW 2026-08-21]`
Confirmed by direct read: the process-lineage family is a **single** novel-edge rule_id behind that
one constant, not a `process_lineage.*` family — the plan's mapping module and Open Decision 3 below
must key on `PROCESS_LINEAGE_NOVEL_EDGE_RULE_ID` itself, never a prefix match. Corner:
`service.disappeared` (`SERVICE_DISAPPEARED_RULE_ID`) is *also* a candidate and is the one family that
already carries a scoped-cleartext exception — relevant to Open Decision 1.

**P4 — Monitoring must be ON for triggers to exist (data dependency, not a capability).**
`learned.json.enabled` (default `false`) gates the structural tick that produces the trigger alerts.
The recommend surface therefore requires `learned.json` ON as a **precondition** (you cannot recommend
containment on signals you are not collecting) **and** its own additional default-OFF opt-in (P5).
Enabling the recommend opt-in while `learned.json` is OFF must fail with an honest error, never
silently enable monitoring.

**P5 — A dedicated, default-OFF opt-in switch for this surface (NEW, this plan).** Surfacing
"consider `<verb> <target>`" is a materially louder, scarier emission than a plain anomaly alert, and
a wrong one is a harm vector (§1). It therefore gets its **own** explicit opt-in, default OFF,
**separate from** `learned.json` (monitoring) and **separate from** the future containment authority
kill-switch (§(e) Slice 7.3+). Three conceptually independent gates; this plan owns the middle one.
Fail-closed: a missing or corrupt opt-in config reads as OFF.

**P6 — Scoped-cleartext exception is the hard ceiling for any cleartext.** Any human-readable target
in the notification body may not exceed the `service.disappeared` precedent: cleartext is permitted
**only** in the local, single-user notification body, **only** where the identity itself is the
actionable signal, and **only** for a target class that already carries such an exception — while the
stored alert record, every `--json` surface, and every LLM-reachable field stay **hash-only**. v0's
default (Open Decision 1) is to add **no new** cleartext beyond what the triggering alert family
already carries.

**P7 — No external service, backend, push, or webhook.** Unlike §(e) Slice 7.4 (remote-device
notification), this surface is purely **local**. It stands up no network surface, no API key, no
central service. (This is precisely why it is buildable now and 7.4 is not.)

## 3. Local testability model

Identical to the observed-incident collectors' model: everything is Node.js, and the only subprocess
(notification delivery) is dependency-injected/mocked in tests (`deliverNotification` is already
passed through `daemon.js` options and stubbed in the existing alert tests). Real macOS delivery is
testable on the dev machine; the Linux delivery branches are covered by mocked `execFile` fixtures +
CI, same division of labor as every shipped collector. No VM is required (consistent with the
dev-machine no-`Virtualization.framework` constraint) because **nothing here executes against a real
host** — there is no mutating primitive that would need a Vault-Tec sandbox (that requirement begins
at §(e) Slice 7.5). Every slice below is fully locally testable end-to-end.

## 5. Safety Analysis (invariant-by-invariant)

- **Read-only by default; no mutating action without an explicit policy/authority gate; no silent
  privilege escalation.** No slice mutates the host; the sole subprocess is the pre-existing
  fixed-argv notification delivery. No authority gate is needed because there is no action to gate —
  and none is *added*, so the absence of a gate cannot be mistaken for a bypassed one. Slice 7.2.d
  asserts this structurally. Privilege is unchanged from the read-only monitoring layer (P2).
- **Never fabricate a security signal; degrade-not-fabricate.** `mapAlertToRecommendation` returns
  `undefined` on any unknown/garbled trigger; a recommendation is emitted **only** when a real, due,
  deterministic anomaly alert exists. Delivery status stays honest `best_effort` (P1). Tests 7.2.a(2)
  and 7.2.c enforce "no trigger ⇒ no recommendation" (`[REVIEW 2026-08-21]` the below-confidence case
  from the original draft's test (3) was folded into the garbled-input case — see Slice 7.2.a's
  TDD-tests note). A wrongly-*targeted* recommendation (the §1 harm vector) is bounded by drawing the
  target only from the triggering alert's own already-validated representation, never a fresh guess.
- **Identity hashed/bucketed at source; never store or emit raw identifiers.** The stored
  recommendation record, every `--json` surface, and every LLM-reachable field carry only the
  hash/bucket representation the triggering alert already used — no new raw-identifier handling is
  introduced (P6, Open Decision 1). §(a)'s hash-vs-raw tension is respected: the surface never maps a
  stored hash back to a live target, and v0 performs no new live re-resolution. Negative tests
  7.2.a(5) assert no raw substring leaks. Any future cleartext is capped at the `service.disappeared`
  scoped exception and confined to the local notification body.
- **Fail-closed alert namespaces; the only LLM path is the gated wakeup — no new LLM path.**
  `[REVIEW 2026-08-21, must-fix]` `containment.*` is **hard-excluded** (`hardExcluded: true`, checked
  second in `classifyAlertNamespace`, immediately after `learned.` — the same, strongest-available
  fencing mechanism the initiative already uses for self-audit findings) and is additionally **absent**
  from `KNOWN_ALERT_NAMESPACES`, so it is structurally un-adjudicable by the LLM regardless of
  `enabled_namespaces` **and** cannot be silently reopened by a later edit that adds a real
  `containment.` branch further down the classifier chain — the recommended verb is chosen by
  deterministic code, never a model prompt (§(c): AGENTS.md cannot enforce; only code can). The
  surface is additionally gated by its own default-OFF opt-in (P5) layered on the `learned.json` kill
  switch (P4). No new LLM path is added; the existing gated wakeup is untouched.
- **No new `execFile` surface without a fixed-argv allowlist.** Zero new `execFile` is introduced;
  delivery reuses `notification-delivery.js`'s existing fixed-argv `osascript`/`open` path, with no
  shell and no interpolation of untrusted values into argv (the notification body is passed as data,
  already the case for every alert). Slice 7.2.d's escalation-lint asserts no new subprocess edge.

**Residual limit, stated honestly (inherited from §(a) Cross-verb themes).** Every guarantee here
runs on the monitored host. A root-level host compromise bypasses all of it (a root attacker acts
directly, needing none of Descartes' machinery). This surface defends the compromised-daemon /
prompt-injected-model threat model — it is not, and is not claimed to be, a defense against a fully
rooted host.

## 7. Open decisions for the operator

1. **Cleartext target in the recommendation body? (the crux.)** v0 default = **no new cleartext**:
   the recommendation names the target in the **same** representation the triggering alert already
   uses (hash-only in stored/`--json`/LLM form; cleartext only where that family already has a scoped
   exception, e.g. `service.disappeared`). The richer alternative = a `service.disappeared`-style
   **live re-resolution** that names the raw target in the **local notification body only** — more
   actionable, but it is the first appearance of the execution-time raw-target re-resolution the real
   verbs need (§(a)), requires a new read capability (P2), and re-opens the hash-vs-raw tension.
   **Recommendation: ship v0 with no new re-resolution; defer the richer form to explicit sign-off**
   (it is arguably a shared prerequisite of Slice 7.5 and better designed there).
2. **Which verbs may be *named*?** All five (throttle/block/revoke/quarantine/kill) are safe to name
   since nothing executes. But recommending `kill` (irreversible) even as text normalizes an
   irreversible suggestion. Option: restrict v0 recommendations to the reversible/observational lean
   (throttle/block/investigate) and withhold `kill`/`revoke` from the recommend map until the
   execution plane exists. **Recommendation: default the map to reversible/observational verbs;
   include `kill` only on operator confirmation.** `[REVIEW 2026-08-21, should-fix]`
   **Reconciliation with the closed enum, made explicit:** `KNOWN_CONTAINMENT_VERBS` (Slice 7.2.a)
   stays the full frozen five-verb enum regardless of this decision — it exists so the boundary tests
   (7.2.d) and the namespace hard-exclude fence every possible `containment.recommend.<verb>` rule_id,
   including ones v0 never emits. If this decision withholds `kill`/`revoke`, then
   `containmentRecommendationRuleIds()` and the deterministic-local-delivery allowlist
   (`alert-intelligence.js`) must register **only** the verbs the v0 map actually emits — an
   implementer must not allowlist an unemitted `containment.recommend.kill` "for completeness," since
   that would create a deliverable rule_id with no code path that ever produces it (dead allowlist
   surface, easy to mis-audit later). Slice 7.2.a's new test (7) above enforces exactly this
   emitted-set-⊆-allowlisted-set direction.
3. **The signal→verb map itself.** It is deterministic CODE encoding Descartes' opinion of "what to
   consider doing" per anomaly, so the operator should review the proposed default map (Slice 7.2.a,
   keyed on the exact rule_id constants per the `[REVIEW 2026-08-21, should-fix]` note there):
   `CANARY_TRIPPED_RULE_ID`/`CANARY_TAMPERED_RULE_ID` → investigate/quarantine;
   `SESSION_COUNT_DROP_RULE_ID`/`SESSION_CHURN_RULE_ID` → investigate;
   `PROCESS_LINEAGE_NOVEL_EDGE_RULE_ID` → consider throttling; `PEER_COUNT_SPIKE_RULE_ID` →
   investigate/consider blocking.
4. **Delivery channel.** Reuse the shipped `defaultNotificationChannel` (macos-native/desktop /
   linux-desktop / syslog / cli) as-is, or give the recommend surface a distinct channel/priority so
   containment recommendations are visually separable from ordinary anomaly alerts?
5. **Toggle shape.** Confirm a **new** default-OFF `containment-recommend.json` opt-in (recommended,
   P5) versus folding the opt-in into an existing config; and confirm the three-independent-gates
   model (`learned.json` monitoring / this opt-in / the future 7.3+ authority switch).
