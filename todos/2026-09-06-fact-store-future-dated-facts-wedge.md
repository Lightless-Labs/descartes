# Fact-store future-dated-facts continuity wedge

**Created:** 2026-09-06
**Status:** deferred bug — pre-existing, independent of the trusted-state step-① reversals (R1/R2/R4)
**Area:** `tools/descartes-cli/src/fact-store.js`, `fact-store-integrity.js`, `fact-store-completeness.js`, `daemon.js`
**Found by:** grounded external review, `docs/reviews/2026-09-06-trusted-state-step1-grounded-review.md` ("Phase-1 'recovery' is an escape hatch" + plan-missed #1); scoped by `docs/plans/2026-09-06-trusted-state-step-1.md` §5.2 and its 2026-09-06 Addendum.
**Related:** [[2026-09-06-trusted-state-step1-operator-signoff]] (the Addendum pulls a bounded retention clamp into the R1 sign-off conditions — this wedge must close first, or the clamp guard is defeated), [[2026-09-06-f2-tier2-fact-store-sliding-anchor]] (shares the continuity-proof substrate; its own acceptance criteria already require "future-dated facts must not count as coverage")

## Summary

A forward-stepped OS clock writes a genuine future-*dated fact record* (not just a ledger loss marker) into `facts.jsonl`. That record permanently pins the store's own "newest observed" high-water mark in the future, which permanently defeats the store's append-continuity proof — collapsing every subsequent read to the honest-but-stuck `"unknown"` status, with no bounded, no-manual-intervention recovery path.

## Mechanism (verified against working tree)

1. **Forward clock → future-dated fact write.** The daemon's structural-tick timestamp is wall-clock-derived: `const ts = options.ts ?? new Date().toISOString()` (`daemon.js:485`). `daemon.js:602` gates the append on `factPoints.length > 0`; `:616` calls `appendFacts(descartesPaths, factPoints, { ts, now: options.now ?? ts, maxBytes: ... })` — `ts` and `now` are the same value on this call whenever `options.now` is unset, which is the normal production tick (a caller-supplied `options.now` could diverge, but nothing in the daemon's own call path sets one). `appendFactPoints` stamps every point with it (`normalizeFactPoint(point, { ts: options.ts ?? options.now })`, `fact-store.js:336`) and appends unconditionally (`:337-339`) before retention ever runs. Nothing bounds a fact's `ts` above `now`; `enforceFactRetention`'s `cutoffMs = nowMs - retentionMs` (`fact-store.js:226`) only evicts records *older* than the window.

2. **The retention pass that ingests the future record itself reports "ok."** `enforceFactRetention` builds its own `live` view straight from `records.filter(isStoredFactPoint)`, taking the max `ts` across the file (`fact-store.js:294-297`, mirrored at the read path `:396-399`). On the pass that appends the future record, `observeFactContinuity(priorLedger, live)` compares `live.newest_ts` (now future) against the *prior* ledger's `last_rewrite_newest_ts` (still a real value) — future > prior, so the `:252-256` append-branch condition (`live.newest_ts <= expectedNewest`) is false and continuity reports `"ok"`. This pass commits `continuity_ok:true` **and** stamps `last_rewrite_newest_ts = outputNewestTs` = the future value (`fact-store-integrity.js:306,370`, via `newestTimestamp`, `:211-216`, a max-over-records function structurally identical to the read path's).

3. **The very next append pins the wedge shut, and the ledger — not the live read — is what carries it forward.** On the next pass with any new record (real-time or not), `expectedNewest` is now that committed future value, and `live.newest_ts` is *still* that same future value (nothing evicts it — see step 4), so `live.newest_ts <= expectedNewest` is now `true` (equal) and `observeFactContinuity` returns `"unknown"` (`fact-store-integrity.js:252-256`). `prepareFactIntegrityLedger` commits `continuity_ok:null` for that pass (`:312`) — and, critically, keeps re-stamping `last_rewrite_newest_ts` to the (still-future) `outputNewestTs` on *every* later pass regardless of branch (`:370` runs unconditionally), so `expectedNewest` can never fall below the future value again. This is why the wedge is permanent, not one-tick: a subsequent *pure read* with zero new appends would, on its own, recompute `observeFactContinuity` as `"ok"` (nothing changed, digest matches, `:259`) — but `buildCompleteness` doesn't trust a fresh recompute over the ledger's own state: `rawContinuityOk = ledger.continuity.continuity_ok` (the committed `null`) flows through `:444/:447` unchanged (it's `null`, not `false`, so the future-break carve-out at `:449` never applies), the `:452` gate fires on `continuityOk !== true`, and `:454` yields `status:"unknown"` (`null !== false`). The stuck value lives in the *ledger*, and every read inherits it.

4. **`factHistoryTrustworthy` → `"history_unknown"`; detectors go dark.** `completeness.status === "unknown"` hits the dedicated branch at `fact-store-completeness.js:62` (`{trust:false, reason:"history_unknown"}`) — a different branch from the `"degraded"` cases at `:66`/`:73` that R1/R2 touch. `constraint-miner.js:366` gates all candidate mining on this trust flag; with no window (`asOfMs=-Infinity`), unwindowed mining goes to zero with **no fixed recovery bound** (per the grounded review's phrasing) for as long as the future record is on disk. (The review additionally lists service/session/peer/process-lineage baselines as consulting the same trust gate — confirmed by grep: `factHistoryTrustworthy` is imported in `canary-baseline.js`, `peer-baseline.js`, `persistence-baseline.js`, `process-lineage-baseline.js`, `service-baseline.js`, `session-baseline.js`, `incident-correlation.js`, `shadow-store.js`, in addition to `constraint-miner.js`; not independently re-traced here beyond confirming the import.)

5. **Manual "delete `integrity.json`" does not recover it, and the record itself is not evictable.** `enforceFactRetention` is reachable in production **only** through `daemon.js:602`'s gate into `appendFactPoints → fact-store.js:350` (grepped: no other call site in `src/`, no standalone repair/GC command). Deleting `integrity.json` bootstraps a fresh ledger on the next pass (`ledger===null`, `fact-store-integrity.js:279-280`), but that pass's `outputRecords` still contains the future record, so it re-stamps `last_rewrite_newest_ts` to the same future value (`:370`) — even the very next completeness read (before any further append) is already stuck at `"unknown"` again (the fresh bootstrap commits `continuity_ok:null` because `bootstrap` forces `continuityObservation = "unknown"` at `:305` regardless of what a live comparison would say), and the pass after that lands right back in step 3's stuck branch. Separately, the record can't age out on its own: age-eviction only drops `tsMs < cutoffMs` (`fact-store.js:226,251`), and a future `ts` is always `>= cutoffMs`; byte-cap trimming keeps candidates newest-first (`:252-265`), so the future record — being the newest by construction — is the *last* one ever evicted. The only escape absent a code fix is hand-editing `facts.jsonl` to remove the offending line, heavier than the (already-insufficient) `integrity.json` deletion the plan's §5.2 leaned on as interim recovery.

## Severity

**HIGH**, but fail-**STUCK**, not fail-open: `"unknown"`/`"history_unknown"` are honest — nothing here lets `status:"intact"` be reached without proof (never-fabricate holds). The cost is availability. Partial mitigant: `descartes learned status` *does* surface the bare word `unknown` (`constraint-store.js:387`; `"unknown"` is in `selectFactStoreCompleteness`'s status whitelist, `:321`) — better than R1/R2's harder-to-discover `history_degraded` case. But it carries no forensic content: `last_corrupt_ts`/`last_schema_invalid_ts`/`last_continuity_break_ts` aren't in that function's field set at all (`:316-330`), `continuity_ok` reads `null`, and `first_degraded_ts` stays `null` too (none of the delta counters that would set it — corrupt/schema-invalid/bytecap/continuity-break — ever fire in this wedge, `fact-store-integrity.js:364`). An operator sees an unexplained bare `"unknown"` with no timestamp and no channel pointing at a future-dated fact.

## Why it matters twice

1. **Standalone, pre-existing bug**, reachable today, independent of the R1/R2/R4 reversals (R1/R2 touch `buildCompleteness`'s `lossAtOrAfter`/`continuityBreakIsFuture` at `fact-store-integrity.js:410`/`:444-451`; `observeFactContinuity` — where this wedge lives — is untouched by either).
2. **Hard prerequisite for the R1 bounded clamp.** The review's minimal-fix #1 states the exact defeat mechanism: *"fix the future-fact continuity wedge first, or `last_rewrite_newest_ts` (itself future) defeats a `nowIso >= last_rewrite_newest_ts` guard."* The Addendum pulls this bounded clamp into the **Phase 1 / R1 sign-off conditions**, superseding plan §9's stale text (still says "no retention clamp" / Phase 3 only — not yet updated to reflect the Addendum). Any clamp keyed off comparing against `last_rewrite_newest_ts` inherits this wedge's stuck-future value and refuses to fire on every pass, so this bug must close (or be explicitly scoped around) before that clamp can be verified to work.

## Fix direction (weigh both — not decided here)

- **(a) Treat an implausibly-future write as an observable, immediately-aged loss**, e.g. at retention time reclassify any record with `ts > now + tolerance` into a new loss channel (a `last_future_fact_ts`-style ledger field, aged the same way as `last_corrupt_ts`) instead of admitting it into `outputRecords`/feeding `outputNewestTs`. Requires a new `tolerance` constant (none exists today — grepped `clockSkew`/`toleranceMs`/`clock_tolerance`, no hits) and, more importantly, **a same-boot-regression guard before it can be unconditional**: under a stepped-*back* clock, every recently-written *legitimate* fact would satisfy `ts > now + tolerance` too, so a naive version would quarantine/drop real history on a clock-rollback attacker — the same class of hazard the plan's §5.2 flags for the ledger clamp, now for fact records. This wants gating on the B-ledger same-boot `clock_regression` distinction (§5.3), not a bare timestamp comparison. Also note the reclassification **cannot fire on the write tick itself** — append and retention share one `now` value that tick (`daemon.js:616`), so the record's `ts` is never later than `now` until wall time is *later* restored; it only becomes detectable on the first post-restore pass.
- **(b) Prove appends by parsing committed bytes, not by comparing newest-ts.** Replace/supplement the `:252-256` check with a structural proof over the byte range beyond `committedBytes` (`:238`) — confirm well-formed appended records regardless of what `ts` any record carries. Must preserve the existing rationale the current check also (incidentally) covers: a ledger written before `facts.jsonl`'s rename can observe the old, longer file, and same-newest-with-excess-records is unprovable rather than trusted (`:249-251`'s comment). Note (b) alone still leaves the future record itself sitting in the store's fact history indefinitely (it never age-evicts, per step 5) — it fixes the *continuity proof* but not detectors reading a future-dated point as legitimate content; that residual overlaps [[2026-09-06-f2-tier2-fact-store-sliding-anchor]]'s "future-dated facts must not count as coverage" requirement.
- Either direction: no new path to a fabricated `status:"intact"`, and no silent content loss — a dropped/reclassified future fact must be recorded as having been dropped.

## Acceptance (a real-path test, no mocked `intactReadResult`)

- Real `appendFactPoints`/`readFactPoints`/`enforceFactRetention` over a real temp store (the `fact-store-integrity.test.js` pattern, not the detector suites' mocks).
- Sequence: one daemon-shaped tick at a forward-stepped clock writes a fact point (`daemon.js:602/:616`'s real call shape, `ts === now`) → restore the clock to real time → further clean ticks.
- Under fix (a), the traced bound is concrete and should be pinned exactly: the first post-restore pass still reads `"unknown"` (its retention pass reclassifies/excludes the future record from *this* pass's own committed output, but `observeFactContinuity` for this same pass still compares the pre-rewrite *live* disk state — which still includes the future record — against the stale prior-committed future value, so it returns `"unknown"` for this pass regardless); the *second* post-restore pass reads a live state already rewritten without the future record, so `live.newest_ts` finally exceeds the now-real committed `expectedNewest` and `observeFactContinuity` returns `"ok"` — plus one full retention window for the newly-recorded loss marker to age out of `buildCompleteness`'s `"degraded"` state. A chosen fix must state and test its own bound; under fix (b) the bound needs separate derivation since the newest-ts comparison is replaced.
- Assert throughout: `status` is never fabricated to `"intact"` while the future-dated write is unresolved.
- Regression-pin: demonstrate today's actual stuck-forever behavior failing pre-fix (`"unknown"` persisting across ≥20 clean passes, including across a mid-sequence `integrity.json` deletion — verified in this write-up: deletion bootstraps a fresh ledger but the very next completeness read is already `"unknown"` again, since bootstrap forces `continuityObservation = "unknown"` unconditionally).

## Open questions

- Tolerance value for fix (a), and whether it should be operator-configurable (mirrors `fact_store_max_bytes`'s precedent in `constraint-store.js`).
- Quarantine (keep the raw fact, flagged, off the trust path) vs. outright drop for a reclassified future record under fix (a).
- The rollback-attacker scope decision the plan itself defers (plan-missed #2 in the grounded review) applies here too: is a same-uid clock-rollback attacker in scope for Phase 1, or only for B-ledger?
- Whether fix (b) still needs *some* plausibility check on `ts` for detector-facing purposes, given it stops treating newest-ts as the continuity signal but doesn't stop a future-dated point from being read as trustworthy content.
- Once implemented, should the new loss channel be added to `selectFactStoreCompleteness`'s field set so `descartes learned status` doesn't repeat the forensic blackout this wedge currently has for the plain "unknown" case?
