## 1. Problem statement & why-now

The 2026-08-11 agentic-intrusion research (`§2.3`) named three structural host-edge gaps this adversary class exploits that a single-host monitor CAN see and did not. Gap 1 (process-lineage novelty) shipped 2026-08-12 (`6238f7e`, HANDOFF SESSION UPDATE 2026-08-12). Two remain:

**Gap 2 — Persistence baseline ("a new service / scheduled job appeared").** Descartes has `service.disappeared` (set-diff, fires when an established entity *vanishes*) but **no appearance detector anywhere** — not for services, not for scheduled jobs. Persistence installation is the canonical post-exploitation move: a new cron entry, a new systemd timer, a new launchd `LaunchAgent`, a new/rewritten unit. The research maps this to TTP #2 (covert C2 via a writable/new service used as a dead-drop) and TTP #8's persistence tail. Worse, `scheduled-jobs.js` is a pure L0 read-only collector with **zero** fact-store / census / baseline wiring today — so a new scheduled job is invisible to Descartes' history at every layer, not merely un-alerted. This is the deepest blind spot the todo names.

**Gap 3 — Credential-file-access signal.** No collector watches modification/access of real sensitive credential files (`~/.ssh/id_*`, `~/.aws/credentials`, `~/.netrc`, and — out of v1, see O6 — `~/.config/gcloud/*`, `~/.npmrc`). The research maps this to TTPs #6/#8/#10/#11 (leaked-credential first-use, privesc, K8s SA-token harvest, cloud-secrets harvest) — all touch credential material on the host edge. The deception/canary tier (`11f94fb`) already ships the exact `lstat`-diff primitive on *planted decoys*; Gap 3 applies that same primitive to *real* credential paths, with an honestly higher false-positive rate and therefore `warning` (not the canary's `critical`). `[REVIEW]` **Honest reach limit:** `lstat`-metadata diff proves rewrite/replace (`mtime`/`ino` change), not a read — a genuine credential READ leaves `mtime` untouched, and v1 ships with `atime` disabled everywhere (O7); see Slice D's notification-wording fix. **Out of scope, stated explicitly:** the source todo (`todos/2026-08-11-agent-intrusion-detection-gaps.md`) names `/proc/self/environ`-class reads under Gap 3; this plan drops that scope silently in the earlier draft — corrected here: a read of another process's `environ` is not observable via `lstat` of any fixed path (there is no stable on-disk file whose metadata changes when `/proc/<pid>/environ` is read), so it is out of scope for this `lstat`-diff mechanism. The shipped process-lineage detector (Gap 1) partially covers the READING process's own spawn/lineage, which is the closest available signal; a dedicated environ-read detector is not part of this plan.

**Why now.** The luna/sol collector pipeline (HANDOFF 2026-08-12) shipped Gap 1 and left these two as "specced follow-ons." The substrate they mirror is all landed and battle-tested (service-baseline census+diff, process-lineage appearance-inversion, canary stat-diff). Building them now closes the persistence + credential-access columns of the §2 detectability map while the pattern is fresh and the seam files are stable. All read-only, default-OFF — no authority plane needed.

### Slice A — Scheduled-jobs fact-store wiring (facts only, NO alert)

**locallyTestable:** true (macOS cron/launchd native; Linux systemd-timer branch via mocked `execFile`).

**Goal:** give `scheduled-jobs.js` the fact-history + census-marker wiring it lacks (P1), so a scheduled-job baseline becomes *possible*. This slice emits **facts only** — it introduces no alert, no rule_id, no `extraCandidates` entry. Pure read-only observation, mirroring how `service.presence`/`service.census` facts exist independently of `service.disappeared`.

**Files touched:**
- `tools/descartes-cli/src/fact-translators.js` — ADD `SCHEDULED_JOB_PRESENCE_FACT_NAME = "scheduled_job.presence"`, `SCHEDULED_JOB_CENSUS_FACT_NAME = "scheduled_job.census"`, `SCHEDULED_JOB_CENSUS_MARKER_ENTITY_KEY = "scheduled_job.census-marker.v1"`, and `factPointsFromScheduledJobsEvidence(evidence, { ts })`. Entity key is a **length-prefixed composite** (NOT a delimiter-joined string — inherit Gap 1's resolved separator-collision fix), built from THREE legs — `kind`, `source`, and a **per-entry identity digest** (see the cron fix below, `[REVIEW 2026-08-21, must-fix]`) — via a `buildScheduledJobEntityKey(kind, source, identityDigest)` helper using the same `length:segment` framing as `buildLineageEntityKey`, so two different (kind, source, identity) triples can never collide. Each segment sanitized via `sanitizeIdentityString` with a bounded `maxLength`; a name field that reduces to empty falls back to `"unknown"` per segment (degrade-not-fabricate, never drop the whole fact silently).
  - **`[REVIEW 2026-08-21, must-fix]` Per-entry identity, not `job.label ?? job.unit ?? job.path`.** A parsed cron job has NEITHER `label` NOR `unit` (`scheduled-jobs.js:151-160` yields `{kind:"cron", source, path, line_number, schedule, user, command}` — no per-entry name field at all), so the naive `job.label ?? job.unit ?? job.path` formula collapses to `job.path` for every cron entry, and `path` is shared by every line in the same file: all user-crontab entries share `"crontab -l"`, all `/etc/crontab` entries share `"/etc/crontab"`, all entries in one `/etc/cron.d/<file>` share that file's path. **Every entry in one crontab collapses to ONE entity key.** A new malicious line appended to an existing (already-established) crontab therefore produces NO new entity key and `scheduled_job.appeared` (Slice B) can never fire for it — the plan's own §1 canonical threat ("a new cron entry") would be silently undetectable except in a previously-empty file. `systemd`/`launchd` entries carry `unit`/`label` and are unaffected — this is cron-specific.
    - **Fix:** name leg = a domain-separated digest of the entry's stable content, NOT the raw command text (hash-at-source — the command line is sensitive and must never appear in `entity_key`): `identityDigest = sha256("descartes.schedjob.cron.v1" + "\0" + path + "\0" + schedule + "\0" + (user ?? "") + "\0" + boundedRedactedCommand).slice(0, 16)`, folded into the composite key as one length-prefixed segment alongside `kind`/`source` (same collision-proofing as the outer composite). `line_number` is explicitly NOT part of identity — pure reordering (a file rewritten with the same entries in a different order) must not read as churn. Editing an existing entry's schedule/user/command IS a real identity change and correctly reads as disappear-then-appear — a rewritten cron command is itself a persistence-relevant event, so this is desired, not a false positive. `systemd`/`launchd` jobs keep `unit`/`label` as their name leg unchanged (they already have real per-entry identity).
- `tools/descartes-cli/src/daemon.js` — `runDaemonIteration`'s structural `factPoints` array: add `...factPointsFromScheduledJobsEvidence(structuralEvidence, { ts }),` alongside the existing `factPointsFromXEvidence` spreads. `scheduled-jobs` is ALREADY a structural sub-collector (its evidence is already collected each structural tick) — no `collectStructuralEvidence`/`activeCollectors`/`defaultDaemonProfile` edit is needed for Slice A. Only the fact-points append is new.
- `docs/reference/collectors.md` — note that `collect_scheduled_jobs` now contributes fact-history.

**Deterministic behavior:**
- One `scheduled_job.presence` fact per returned job (deduped by composite entity key; two DISTINCT cron entries in the same file now produce two DIFFERENT keys per the per-entry digest above — the residual "two jobs collapse to one key" case is now limited to a genuine content collision, which remains an acceptable set-membership corner case).
- Exactly ONE `scheduled_job.census` marker per `status:"ok"|"warning"` tick (including a genuine zero-job tick — a real, distinguishable fact), `confidence: 0`, own `fact_name`.
- `[REVIEW 2026-08-21, must-fix]` `census_state` = `"complete"` iff `summary.unavailable_count === 0` **AND** `evidence.truncated !== true`; otherwise `"partial"`. The envelope-level `truncated` flag (`scheduled-jobs.js:538`, `allJobs.length > jobs.length || probes.some(p => p.truncated)`) subsumes BOTH the total-vs-returned leg AND every probe-level truncation (directory-listing caps, launchd candidate caps, truncated cron-file reads — P2) — using it instead of re-deriving from `total_count === returned_count` closes the fabrication path where jobs are dropped before `allJobs` is ever assembled. On `status:"unable"`/`"unknown"` → NO marker (the collector never ran a real census).
- Per-tick entity count is already bounded by `job_limit` (80 default, P6) — no new cap needed.

**TDD tests** (append to `test/fact-translators.test.js`, mirroring `factPointsFromServiceEvidence`'s table):
- envelope missing / `status:"unable"` → `[]`.
- `status:"ok"` with jobs → one presence fact per deduped job + exactly one census marker (`confidence:0`).
- **P2 partial trap:** `total_count > returned_count` (fairness-capped) with `unavailable_count === 0` → marker MUST read `"partial"`, not `"complete"`. Separate case: `unavailable_count > 0` with `total_count === returned_count` → also `"partial"`.
- **`[REVIEW 2026-08-21, must-fix]` probe-truncation trap:** `summary.total_count === summary.returned_count` AND `summary.unavailable_count === 0` (the naive formula's "complete" case) BUT `evidence.truncated === true` (a probe reports `truncated: true`, e.g. a capped periodic-directory listing or launchd candidate list, with the drop happening before `allJobs`) → marker MUST read `"partial"`. This is the primary regression test for the P2 fabrication class.
- zero jobs but collector ran (`status:"ok"`, empty list, `truncated: false`) → census marker present, `census_state:"complete"`, zero presence facts (distinguishable from "collector failed").
- **`[REVIEW 2026-08-21, must-fix]` cron entity-key tests:** two DISTINCT entries in one crontab (same `path`, different `schedule`/`command`) → two DIFFERENT entity keys. A new line appended to an existing (previously-established) crontab → the new line's key does not match any prior key (this is the regression test proving Slice B can later fire on it). Pure reordering of the same entries (same content, different `line_number`) → identical set of entity keys, no spurious appear/disappear.
- composite-key collision negative test: `(cron, /etc/cron.d/a, b->c)` and `(cron, /etc/cron.d/a->b, c)` produce DIFFERENT entity keys (length-prefix framing) — still holds with the identity-digest name leg.
- hash-at-source: a job label/command shaped like an IP / hostname / username / ISO timestamp does not survive verbatim into `entity_key` beyond the digest/sanitizer bound (composite key is structurally bounded; the raw command text never appears in any fact field).

**Adversarial-verify focus:** the P2 census-state trap under probe-level truncation (the single most likely correctness miss — a reviewer must confirm `census_state` is driven by the envelope `truncated` flag, not re-derived from `total_count`/`returned_count`/`unavailable_count` alone); the cron per-entry identity fix (confirm a new line in an existing crontab yields a new entity key, and that pure reordering does not); and that Slice A truly emits no alert candidate (grep the diff for any `extraCandidates`/rule_id addition — there must be none).

## 5. Safety Analysis (each invariant → how the plan upholds it)

- **Read-only by default. No mutating action, no privilege escalation.** Slice A/B/C reuse the already-approved `scheduled-jobs.js`/`services.js` fixed argv; Slice D is `fs.lstat`-only (strictly smaller than any existing collector). No slice kills/revokes/blocks/quarantines/rewrites anything. No new `execFile`/shell surface. - **NEVER fabricate a security signal. Degrade-not-fabricate.** This is the load-bearing invariant for novelty detectors. Upheld by: (a) census-marker `census_state` derived from the collector's own truncation/availability, never inferred (P2); (b) `"partial"`/`"unknown"`/markerless tick-groups excluded wholesale from both the historical union and the latest comparison (P8); (c) persistent cold-start lockout on any per-store loss/corruption — self-heal-and-immediately-fire is explicitly forbidden (mirrors `process-lineage-baseline.js`); (d) the freshness gate suppresses claims on stale history; (e) Gap 3 existence-gating + permission-degrade + silent cold-start seeding — an absent/unreadable credential path is never a fabricated "untouched", and a first-sight path never fabricates a trip (P5, P4). **Behavior on incomplete history: emit nothing, cold-start.** The remaining exposure (a silently-truncated fact-store below the detector's own store) is the SERIALIZATION dependency P8 — these detectors depend on `todos/2026-08-11-fact-store-completeness-detector-hardening.md` for a durable completeness signal, and until it lands they fail closed the same way the shipped lineage detector does.
